Feature-Plan v2 · Kassenbuch CREDO

Beleg-Upload + konfigurierbares DMS-Mapping + Sammel-Export

Jede Buchung kann mehrere Belege (PDF/JPG/PNG) erhalten. Pro Mandant wird konfiguriert, welche Buchungsfelder unter welchem Schlüsselnamen in den Swiss-QR-Code wandern — damit das DMS jede Buchung automatisch zuordnen kann (Datum, Konto, Kostenstelle, Mandantennummer, Belegart, …). Der Admin lädt für einen Zeitraum eine einzige PDF mit QR-Trennseite vor jedem Belegdokument herunter.

model DmsFieldMapping {
  id          String        @id @default(uuid())
  schoolId    String        @map("school_id")
  source      FieldSource   // BOOKING_FIELD | CONSTANT
  bookingField BookingField? // gesetzt wenn source = BOOKING_FIELD
  constantValue String?      @map("constant_value") // gesetzt wenn source = CONSTANT (z.B. "1" für Fibu)
  dmsKey      String        // frei wählbar, z.B. "sichtid1"
  format      FieldFormat?  // nur sinnvoll bei BOOKING_FIELD
  maxLength   Int?          @map("max_length") // Auto-Truncate (zeichenweise) — nur bei Text-Feldern sinnvoll
  sortOrder   Int           @default(0) @map("sort_order")
  isActive    Boolean       @default(true) @map("is_active")
  includeOnSeparator Boolean @default(true) @map("include_on_separator")

  school      School @relation(fields: [schoolId], references: [id], onDelete: Cascade)

  @@unique([schoolId, dmsKey])
  @@map("dms_field_mappings")
  // CHECK: (source=BOOKING_FIELD AND bookingField IS NOT NULL)
  //     OR (source=CONSTANT       AND constantValue IS NOT NULL)
}

  COUNTER_ACCOUNT_NAME

  COST_CENTER_NAME

  TAX_KEY
  BELEGART_CODE

5.2 Verhalten

  • Drag-Sort bestimmt die Reihenfolge der Keys im QR-Payload.
  • DMS-Schlüssel ist pro Schule eindeutig. Validierung: keine Pipe |, kein Doppelpunkt :, max. 40 Zeichen.
  • Format nur dort sichtbar, wo es Sinn ergibt (Datum → Datums-Formate, Betrag → Zahlenformate, …).
  • „aktiv" AUS = Feld bleibt in der Konfiguration, wird aber nicht in den QR geschrieben (z.B. Verwendungszweck ist datenschutz-empfindlich, drum ausgeschaltet).
  • Vorschau-Button ruft POST /dms-mapping/preview auf und zeigt:
    1. die generierte Unstructured-Data-Zeile
    2. den daraus erzeugten QR (Bild)
    3. einen Längenwarner (s.u.)

5.3 Längen-Constraint & Auto-Trunkierung

Die Swiss-QR-Unstructured-Data-Zeile darf max. 140 Zeichen sein. Mit 9 Mapping-Zeilen ist das schnell erreicht, vor allem wegen freier Texte wie textindokument.

Mehrstufige Strategie (Builder, deterministisch & O(n))

  1. Sanitize jeder Wert: | und : → Leerzeichen, Zeilenumbruch/Tab → Leerzeichen, doppelte Leerzeichen kollabieren, beidseitig trimmen. (Sonst zerschießt der Wert das Key-Value-Format.)
  2. Field-Truncate: wenn maxLength gesetzt und Wert länger → auf maxLength − 1 kürzen, „…" anhängen. Code-Point-sicher (Array.from + slice + join), damit Umlaute/Mehrbyte-Zeichen nicht in der Mitte abgeschnitten werden.
  3. Zeile zusammenbauen, mit | joinen.
  4. Hard-Cap-Check: wenn Zeile > 140 Zeichen → ExportError mit klarer Meldung „QR-Payload überschreitet 140 Zeichen (gemessen: 152). Bitte ein Feld deaktivieren oder maxLength eines Textfelds verringern." Kein stilles Abschneiden.

Pre-Flight-Check beim Bulk-Export

Vor dem Generieren der Mappe iteriert der Server einmal über alle gefilterten Buchungen und prüft die längste Payload — das ist ein billiger Query (MAX(length(description))) + ein In-Memory-Build-Lauf. Bei Overflow: Export bricht vor dem ersten erzeugten Byte ab und zeigt dem Admin, welche konkrete Buchung das Problem ist. kein verschwendetes PDF

Performance-Garantien

OperationKomplexitätBemerkung
Mapping laden1× pro Schule, gecacht (LRU 10 min)Buchungen einer Schule teilen sich die Konfig — kein N+1.
SanitizeO(L) — L = WertlängeEine einzelne .replace(/[|:\s]+/g, ' ').trim()-Kette, kein Regex-Backtracking.
TruncateO(maxLength)Array.from(str).slice(0, maxLength-1) — nur bei Bedarf.
Hard-Cap-CheckO(1)Reines length-Property.

→ Für 5.000 Buchungen im Bulk: < 50 ms reine Builder-Zeit, dominiert vom DB-Read und PDF-Encoding.

Im Mapping-Editor: Live-Zähler zeigt die aktuelle Payload-Länge unter der Tabelle. Ab 120 Zeichen gelb, ab 140 rot mit „Speichern blockiert". Der „Vorschau"-Button rendert die echte Builder-Ausgabe inklusive Sanitize/Truncate.
Realitätscheck Default-Seed: die fixen Keys (mandant, dokumentart, datumindokument1, …, belegnr) verbrauchen mit den 8 Pipes und Doppelpunkten ~110 Zeichen reine Struktur. Es bleiben also ~30 Zeichen für alle Werte zusammen. Bei einer typischen Buchung (Datum + Belegart + Konto + Betrag + Belegnr) ist das bereits eng — textindokument wird de facto auf ~10 Zeichen Restbudget truncated. Empfehlung für den Praxisbetrieb: textindokument entweder auf maxLength 20 setzen oder per Default deaktivieren (Beschreibung steht ja im Klartext auf der Trennseite). Im Seed lasse ich es bei 60 — beim ersten Export-Fehler weiß der Admin, was zu tun ist.

6Swiss-QR-Payload (dynamisch)

SPC-Header bleibt identisch zur Referenz — die unstrukturierte Daten-Zeile wird aus dem Mapping generiert. Damit kann die bestehende n8n-DMS-Pipeline ohne Anpassung weiterlaufen, sobald sie auf die konfigurierten Keys angepasst ist.

6.1 Generierungs-Logik (Pseudocode)

// Verbotene Steuerzeichen für unser KEY:value|… Format
const SANITIZE = /[|:\r\n\t]+/g;
const COLLAPSE_WS = /\s{2,}/g;

function sanitize(s) {
  return String(s ?? '').replace(SANITIZE, ' ').replace(COLLAPSE_WS, ' ').trim();
}

function truncate(s, maxLength) {                       // code-point-sicher
  if (!maxLength) return s;
  const chars = Array.from(s);                          // teilt nach Unicode-CP
  if (chars.length <= maxLength) return s;
  return chars.slice(0, maxLength - 1).join('') + '…';
}

async function buildQrPayload(booking, fileIndex, totalFiles) {
  const mapping = await getMappingCached(booking.schoolId); // LRU, 10 min

  const kv = mapping.map(m => {
    const raw = m.source === 'CONSTANT'
      ? m.constantValue
      : resolveField(booking, m.bookingField, fileIndex, totalFiles);
    const formatted = m.format ? applyFormat(raw, m.format) : raw;
    const safe = sanitize(formatted);
    const capped = truncate(safe, m.maxLength);
    return `${m.dmsKey}:${capped}`;
  });

  const unstructured = kv.join('|');
  if (unstructured.length > 140) {
    throw new ExportError(
      `QR-Payload überschreitet 140 Zeichen (${unstructured.length}). ` +
      `Buchung ${booking.id}: Feld deaktivieren oder maxLength reduzieren.`
    );
  }
  return assembleSpcLines(booking.school, booking.amount, unstructured);
}

8.1 Sortierung im Bulk-PDF festgelegt

ORDER BY schoolId ASC, bookingDate ASC, receiptNumber ASC — die Belege erscheinen also pro Schule chronologisch und innerhalb desselben Tages in Belegnummer-Reihenfolge. Das DMS liest die Mappe dann in derselben Reihenfolge ein, in der die Buchungen im Kassenbuch stehen.

8.2 Cover-Summen festgelegt

Aufschlüsselung der Beträge im Cover pro Konto (Soll- und Habenbeträge getrennt). Bei Multi-Mandant-Export wird der Cover zusätzlich pro Schule gruppiert.

11Compliance: GoBD & DSGVO

Kassenbücher fallen unter GoBD: Belege 10 Jahre, unveränderbar, maschinell auswertbar, mit Audit-Trail.
  • Re-Upload erzeugt neuen Record; alter bleibt mit deletedAt.
  • Audit-Trail in AuditLog mit User, IP, Zeit, vorher/nachher.
  • Kein automatischer Hard-Delete-Job. Bei Bedarf manuell nach 10 Jahren.
  • Bulk-Export erzeugt Audit-Eintrag mit Filter-Parametern + PDF-SHA-256 (Reproduzierbarkeit).
  • DSGVO: Recht-auf-Löschung steht nicht über Aufbewahrungspflicht.

12Was du ggf. vergessen hast

  1. Belege bei Storno. Storno erbt Referenz auf Belege des Originals — kein Re-Upload; im Bulk einmal mit Hinweis „Storno zu 2026-00123".
  2. Belege bei Split-Buchungen. An Master-Zeile der Split-Gruppe hängen, im UI bei allen Mitgliedern anzeigen.
  3. Performance. Streaming-Response, Async-Job ab ~500 Buchungen, PDF-Komprimierung.
  4. Inline-Vorschau statt Download beim Sichten — schneller im Alltag.
  5. Doppel-Upload-Erkennung via SHA-256.
  6. Reihenfolge der Belege per Drag-Reorder im Popover.
  7. Klartext-Fallback auf der Trennseite falls QR-OCR im DMS versagt (bereits im Layout §7).
  8. Cover-Seite mit Inhaltsverzeichnis, Summen, PDF-Hash.
  9. Backup-Strategie für das Volume ergänzen (Postgres-Backup deckt das nicht ab).
  10. Dashboard-Spaltenreihenfolge: 📎-Spalte in COLUMN_DEFS + Default-Order ergänzen, sonst sieht sie keiner.
  11. Mapping-Vorschau-Längencheck: bei langen Beschreibungen kann der QR über 140 Zeichen kommen — Hard-Block bauen.
  12. Mandant-Switch im Admin-Bulk-Export: Wenn mehrere Schulen ausgewählt sind und jede ihr eigenes Mapping hat — Mapping muss pro Buchung nach booking.schoolId gezogen werden, nicht global.
  13. Sortierung im Bulk: Standardmäßig nach schoolId, bookingDate, receiptNumber — damit das DMS nach Mandant gruppiert eingelesen werden kann.
